# Free demo deployment

The current target is a small demo with no paid infrastructure: Vercel for the
portal/customer web app, Render Free for the API, Supabase Free for PostgreSQL
and private uploads, and a separate free Redis service. The root `render.yaml`
creates only one Free API service; it creates no paid database or Redis instance.

## 1. Create a Supabase Free project

Create a dedicated Nexvolt demo project in a Free organization. Choose a region
near the API (Render is configured for Singapore). Save the database password in
a password manager. A Supabase account alone does not create the database.

Use the project's **Connect** dialog to copy the **Session pooler** URI (port
5432). Use its exact hostname and `postgres.PROJECT_REF` username. Insert your
URL-encoded database password and require TLS (`sslmode=require`). Session mode
provides IPv4 connectivity for the long-running API; do not substitute the
transaction pooler on port 6543. Limit Prisma connections for the demo, for example
with `connection_limit=3` in the URI query parameters.

Disable the Supabase Data API for this dedicated project before migrating the
application tables. Nexvolt uses Prisma and its own API authorization; these
tables have no Supabase RLS policies. Disabling the Data API prevents unintended
REST access to the application schema. Supabase Auth is not used for Nexvolt login.

The migrations create `postgis`, `btree_gist`, and `pgcrypto` in the application
schema. Use a new project where these extensions have not been manually installed
into a different schema. If an extension is already installed elsewhere, inspect
its schema and resolve the search path before migration; do not drop it blindly.

## 2. Configure private Supabase uploads

In Storage, create a **private** bucket named `nexvolt-private`. In Storage's S3
configuration, generate S3 credentials and copy the exact endpoint and region.
These are separate from the project's publishable/anon key and service-role key.
Keep the S3 secret only in API hosting secrets.

Set on the API:

```text
S3_ENDPOINT=https://PROJECT_REF.storage.supabase.co/storage/v1/s3
S3_REGION=<region copied from Supabase>
S3_BUCKET=nexvolt-private
S3_ACCESS_KEY_ID=<generated S3 access key>
S3_SECRET_ACCESS_KEY=<generated S3 secret>
S3_FORCE_PATH_STYLE=true
S3_AUTO_CREATE_BUCKET=false
```

Copy the real endpoint from the dashboard rather than assuming its format.
`S3_PUBLIC_ENDPOINT` can remain unset. The existing AWS SDK adapter will use the
configured S3 endpoint for private uploads and signed downloads. Verify browser
PUT/GET requests, MIME validation, and signed URL handling after deployment.

## 3. Configure free Redis

Create a Redis Cloud **Free** database (not a paid trial), set its eviction policy
to `noeviction`, and copy its connection URI into Render's `REDIS_URL` secret.
Use TLS if the selected free plan supports it; confirm the provided URI rather
than changing its scheme blindly. Check that its connection limit accommodates
the API and BullMQ workers. Free Redis Cloud has no disk persistence: queued work
can disappear on restart. This deployment is for demos only.

## 4. Deploy the free API

Create a Render Blueprint from `codex/staging-deployment` (or `main` after merge)
and root `render.yaml`. Confirm the service's plan is **Free**. Enter the external
Supabase/Redis secrets above, plus:

- `PII_ENCRYPTION_KEY`: `openssl rand -base64 32`; preserve it securely.
- `API_PUBLIC_URL`: the actual API HTTPS origin allocated by Render.
- `CORS_ORIGINS`: exact portal and customer origins, comma-separated.
- `TWILIO_ACCOUNT_SID`, `TWILIO_AUTH_TOKEN`, `TWILIO_VERIFY_SERVICE_SID`.

JWT and OTP HMAC secrets are generated by the Blueprint. The API uses
`NODE_ENV=production`, `LOCAL_DEMO_MODE=false`, and `OTP_PROVIDER=twilio_verify`.
Remove `OTP_EMULATOR_FIXED_CODE`. Twilio SMS is separately metered; use only
eligible trial allowances if your requirement is no spend. Account creation
alone does not guarantee free SMS delivery.

Free Render services cannot run pre-deploy hooks or one-off jobs, so the Docker
command runs `prisma migrate deploy` and only starts the API if migrations pass.
Migrations therefore also run on cold starts; keep schema changes compatible
with the prior application version. Do not run reset/fictional seeds against the
hosted database. For first-admin setup, run `infra/bootstrap-admin.sql` using an
authenticated operator PostgreSQL client connected through Supabase's pooler.

Add Razorpay test credentials together when payment testing is ready; without
them, login and non-payment flows can be configured but checkout remains disabled.

## 5. Connect the frontends

On the portal's Vercel project, configure and redeploy:

```text
NEXT_PUBLIC_API_URL=https://YOUR-API
API_INTERNAL_URL=https://YOUR-API
NEXT_PUBLIC_S3_ORIGIN=https://PROJECT_REF.storage.supabase.co
```

`NEXT_PUBLIC_S3_ORIGIN` must match the origin of the actual S3 endpoint, without
the `/storage/v1/s3` path. The browser CSP is built with this value. No database
password or S3 secret belongs in Vercel's public environment variables.

Export the customer app with `EXPO_PUBLIC_API_URL` pointing to the hosted API.
Its Expo web output is a single-page app; a separate Vercel static project needs
the shared package build, Expo export, `dist` output directory, and a fallback
to `index.html` for application routes. Customer deployment configuration and
hosted browser verification still need to be completed.

## Verification and free-tier limits

Use `scripts/check-deployment.mjs` after all origins are known. Its full readiness
check expects Razorpay configuration as well as healthy database, Redis, and
storage. Then verify real OTP delivery, all three roles, private uploads, and
test payments. Provider configuration flags alone do not prove credentials work.

Render sleeps after idle periods, so initial requests can be slow and maintenance
jobs stop while it sleeps. Supabase free projects can pause after inactivity.
Free Redis does not provide durable queues. Stay within each provider's free
allowances and do not enable paid upgrades. The existing paid AWS templates are
not needed for this deployment.
